目标，是围绕你的智能体构建一套软件，为某一种具体工作提供所需的上下文、工具与方法。

[@garrytan](https://x.com/garrytan) 曾这样概括：

> 要么作为一套记录系统死去，要么活得足够久，最终成为一个领域专用框架。
>
> ——[Garry Tan](https://x.com/garrytan/status/2098666551629267324)

这句话源于 [Jessy Huang](https://x.com/goodhartproof/status/2098523476189745314) 的观察：

> 我昨天刚参加了 YC Demo Day。除了硬件和实体产品，基本上每个人都在构建某种领域专用框架。

可人们真正想实现的究竟是什么？你真的需要打造自己的智能体框架吗？如果你长期与智能体协作——无论是推进一个项目，还是深耕某个专业领域——我认为你需要三样东西。

## 1. 能够延续的知识与工作

下一次会话应该可以带着完整上下文，接着上一次的工作继续往下走。比如，一项决策应该始终与支撑它的证据和假设相连，也要与建立在这项决策之上的后续工作相连。你和智能体都需要能够沿着这些联系追溯，并在情况发生变化时重新审视它们。

## 2. 适合你工作方式的系统

比如，研究者需要追踪引用，并比较不同论断背后的证据；一家公司可能把客户历史保存在 CRM，把交付计划放在项目管理工具里，再把财务假设写进电子表格。对客户许下的一项承诺可能同时影响三者，可这些信息往往分散在三个互不相通的系统里。

我想主张的是：不妨用你和智能体基于自有数据共同构建的定制应用，替换这些割裂的工具，并把一切放进同一个工作空间。你应该能够塑造智能体处理信息的方式，也应该让这套系统随着你的实践不断演化。

## 3. 可复用的基础

你需要把领域知识、成熟实践，以及自己在实践中学到的应用方法结合起来。你的工作流可能包含一套研究规程，也可能是团队在承诺交付日期前必须执行的步骤。知识系统应当对这些工作流进行建模，让你和智能体都能遵循它们，并持续改进。

你还需要连接智能体的方法，以及基于数据构建视图的能力，比如证据表格，或用于管理客户承诺的周计划。另一位研究者或顾问应当可以复用这套基础，再根据自己的工作加以调整。

[@balajis](https://x.com/balajis/status/2016443010360414610) 描述了其中一部分：

> 如今，许多数字化工作的本质，都是为 AI 模型准备上下文。
>
> 把文件整理进文件夹，给所有东西正确命名，按合适的顺序介绍背景，最后再用清楚的书面英语要求 AI 完成任务。

但我认为，事情远不止于此。把工作显式表达出来，也为我们围绕它塑造软件提供了基础。

## 知识系统

一套知识系统会把以下内容汇集到一起：

- **领域对象与关系：**你的领域里真正重要的事物，比如一项论断，以及支撑它的研究。
- **知识与证据：**我们知道什么、这些知识来自哪里，以及你如何解释它们。
- **工作方法：**你的流程与最佳实践，通过指令、技能、工具和检查机制表达出来。
- **持续推进的工作：**你正在研究的问题和项目，以及其中的决策与结果。
- **交互界面：**探索这些材料、引导工作和审查变更的不同方式。

这些部分可以共同发展。你构建的是一个环境：它既体现你知道什么，也体现你如何运用这些知识开展工作。所谓**知识工作工程**，指的就是设计这种环境。

## 智能体仓库

**智能体仓库（agent repo）**，是把知识及处理这些知识所需的能力封装在一起的代码仓库。

在 [Ars Umbris（@arsumbrisai）](https://x.com/arsumbrisai)——我们正在为知识系统打造的本地优先框架与工作空间——中，一个智能体仓库可以包含：

- **用类型化 Markdown 表达的知识：**例如，一项论断可以是一个对象，与支持或反驳它的原文段落建立明确关系，同时记录你自己的问题和计划开展的实验。
- **智能体能力：**例如，说明如何提取、审查论断的技能，以及使用图查询追踪共同证据的 MCP 工具。
- **交互界面：**例如，用于探索文献的引用图，或把论断与原始出处并排打开的审查面板。

工具和界面的代码也可以放在同一个仓库里。这样，你和智能体既能处理知识本身，也能构建处理这些知识的环境。

更妙的是，这些仓库可以像代码包一样相互依赖。一个研究项目可以同时组合方法库、论断提取包，以及用于比较证据的 UI 组件；你自己的论文和问题，则继续留在自己的项目中。

我们的类型引擎允许 Wiki 链接跨越不同仓库：

```markdown
[[research methods::method-library]]
```

是不是很酷？这条链接指向 `method-library` 依赖中的对应笔记。引擎会解析链接，还能检查跨仓库的类型化关系。这样，各自独立维护的知识库就能组成一张可统一查询、可继续构建的图。

你可以在共享知识库的原始仓库里完善它，同时把自己的解释和工作留在个人仓库。当然，一个包即使只包含一套可阅读的知识库，本身也可能很有用。把方法库、应用方法的技能和审查结果的界面组合起来，其他人就能把这套知识用到自己的材料上。

## 让知识库像代码库一样运转

软件行业已经发展出许多模式，让不断扩大的代码库依然可理解、可维护、可修改。我们希望把类似的模式引入知识领域：

- 面向你的领域定制的类型系统；
- 对缺失信息和失效引用的诊断；
- 可以导入并组合的软件包；
- 用于浏览和重构工作的 IDE；
- 记录思考如何变化的版本历史。

Ars Umbris 通过类型引擎、智能体框架和宿主应用——也就是工作空间应用——把这些能力整合到一起。类型引擎把你的多个仓库读取为一张统一的类型图。它的诊断会向你和智能体提供反馈，比如：「这条记录缺少必填字段」，或者「这条引用指向了错误类型的对象」。

智能体框架通过 MCP 提供工具，并以你所用编程智能体框架能够识别的格式交付技能。目前，我们已经为 Claude Code 和 Codex 做好了适配器。一切都可以扩展，因此你可以与智能体一起，为其他框架构建新的适配器。

编程智能体原本就是为代码库设计的：它们可以浏览文件、实施修改，并根据诊断采取行动。我们的假设是，如果以类似方式组织领域知识和工作方法，这些智能体也能把同样的能力带进科研或企业经营。

为每个领域单独打造一套框架，也意味着智能体工具不断发展时，你必须同步维护这些框架。我们可以直接建立在现有框架之上，把领域专属的工作集中在可复用的软件包与定制应用中。

而定制应用需要一个运行环境。如果你基于客户笔记构建了一套 CRM，它理应能够直接在你平时工作的环境中打开。宿主应用提供了这个运行时，以知识图作为所有应用共享的数据层——事实上，你的应用与视图本身也属于同一套基础。规划视图可以直接处理相同的承诺数据，不必再搭建独立数据库或单独部署服务。

同一个类型系统描述你的知识、工具接口和视图配置。我们内置的工具与视图，也使用相同的扩展机制。一次性可视化可以帮助你回答某个具体问题；每周都会使用的视图，则可以成为工作空间里持久存在的组成部分，和它所支持的方法一起接受版本管理与持续改进。

我认为，这将成为 2027 年知识工作领域最重大的变化之一。智能体可以帮助你把工作方法显式化，并写出实践这些方法所需的软件；一套共享框架为这些软件提供运行场所，也让其他人能够在其上继续构建。

## 把一项决策与它创造的工作连接起来

假设某位客户表示：只要你能在 12 月前交付某项功能，他们就会签约。你希望这项承诺始终与对应功能，以及讨论该承诺时的对话相连。可以用一个类型来描述这种关系：

```yaml
# commitment.type.yaml
fields:
  feature: feature*
  deadline: Date
  source: source*
```

`feature` 和 `source` 是你可以在工作空间中自行定义或复用的类型。星号代表这里引用了该类型的一个对象；`deadline` 使用内置的 `Date` 类型。

接下来，一条 Markdown 笔记就可以使用这一定义：

```markdown
---
type: commitment
feature: "[[account export]]"
deadline: 2026-12-01
source: "[[acme sales call]]"
---

如果 12 月前提供账户导出功能，Acme 就会签约。
```

这类似于在代码中定义一个对象必须具备的结构。如果缺少 `source`，或者某条引用与预期类型不符，引擎就可以报告问题。我们的自定义类型语言还支持约束取值，并随着模型发展扩展现有类型。

然后，把功能与实现它所需的工作连接起来，并记录接受这项承诺的决策及其背后的假设。销售团队可以使用管线视图——也就是直接在应用中查看和更新交易的组件；工程团队则可以查看相关工作的规划视图。

假设之后你发现，某项集成所需的时间远超预期。智能体可以沿着已有结构追踪关系，把需要审查的信息呈现给你。至于延期意味着什么、该如何向客户解释，最终仍要由你决定。

也许审查会揭示：你总是在核实集成工作量之前就承诺交付。于是，你把这项检查加入「审查新承诺」的方法中，并要求在接受决策前显示检查结果。下一笔交易因此受益于上一笔交易的经验；而这项检查存在的原因，也始终与促使你添加它的那次经历相连。

## 构建一个与研究共同发展的研究环境

再看一个具体例子。想象你正在与一位准备文献综述的研究者共同构建工作空间。对方手中有 10 篇论文，看起来都支持同一个结论；但其中几篇论文复用了同一套数据，或重复引用了同一项原始结果。研究者需要判断：这里究竟存在多少相互独立的证据。

先从一项论断与一个来源之间的关系开始。下面是我在研究试验平台中探索的一套模型的简化版本：

```yaml
# claim.type.yaml
fields:
  grounds: grounding&[+]
```

一项论断必须至少包含一条依据记录。每条依据记录都要说明：某个来源对这项论断说了什么，以及这个来源是通过多直接的方式获知它的。

```yaml
# grounding.type.yaml
fields:
  of: source::au-base-types*
  stance: [asserts, denies, observes]
  basis: [observed, reported, inferred]
```

`source` 类型来自共享的基础包。列表定义了 `stance` 与 `basis` 允许使用的值。`basis` 用于区分来源是亲自观察到某件事、转述了某件事，还是通过推理得出它。

以一项虚构研究为例，一条论断笔记可以写成这样：

```markdown
---
type: claim
grounds:
  - ^: g1
    of: "[[feedback study^result-1]]"
    stance: asserts
    basis: observed
---

# 在本研究中，每周反馈组的完成率更高

论文报告称，每周反馈组的完成率更高
（参见 [[^g1]]）

这一结果是否适用于我们的课程，仍待研究。
```

当然，你也可以创建一种类型化的「问题」对象，再把它链接到这里。

`of` 链接指向已捕获来源中的一段标记文本。这条依据记录嵌在当前笔记中，但类型也允许它链接到一条独立的依据记录。`^: g1` 为这条依据分配了一个 ID，`[[^g1]]` 则让正文可以精确指向它；当一项论断拥有多条依据时，这一点尤其有用。

如果智能体遗漏了依据记录，或者使用了未知的 `stance` 值，引擎就能报告问题。一个来源可能支持某项论断，也可能否定它；把这种归属关系记录下来，便能留待审查。

**必须强调：**这些结构并不能判定一项论断是真是假，也不能判定某个来源是否真的足以支持它。但它们提供了可以由你或智能体沿着追踪、从语义层面检查的结构。

因此，这些类型是我们使用类型引擎提供的基础构件，为这套研究实践自行定义的。我们可以继续发展模型，把论文和论文背后的实际研究区分开，再把研究与所用数据集连接起来。我们自己的问题与猜想，也可以拥有各自的类型。

论断提取技能可以要求智能体保留这些区别，并把每项论断与原始出处逐一核对；工具可以查询已记录的关系，找出共享同一项研究或同一套数据的论断；比较视图可以把它们的方法和结果并排呈现；引用图则提供另一种探索相同材料的方式。于是，研究者可以从「10 篇论文看似得出了相同结论」，进一步转向对其背后证据的调查。

现在想象一下，这次综述仍留下某个未决问题。研究者把问题记录下来，提出一项实验，并将实验与有待检验的假设相连。结果出来后，它们会进入同一个环境；日后的综述可以继续分析这些结果支持或挑战了哪些结论。

研究方法本身也可以拥有一套知识库。一个研究方法包可以解释不同的偏差来源，以及为什么不同研究设计能够支撑不同程度的结论。智能体在帮助研究者设计类型或修改审查流程时，可以查询这套知识。例如，关于「共享证据」的知识，可以决定提取技能需要记录哪些关系，以及查询工具应该寻找哪些模式。方法背后的推理，可以与应用这些方法所需的能力一起流转。

顺便说明：我没有科学研究背景。这是我第一次为自己的研究尝试构建这样的东西，这里只是拿它作为演示。

## 如果由我开始构建知识系统

先从一项你确实需要完成的工作开始。

假设你要回顾上个季度，以决定下一阶段该把精力放在哪里。把项目笔记和成果带进工作空间，然后与智能体一起梳理：当初预期发生什么，实际又发生了什么。把决策与支撑它的证据保存下来，也记录未来需要重新审视的开放问题。你的上下文和结构，会在推进复盘的过程中自然生长。

接下来，寻找那些持续有意义的区别。如果一项决策建立在某个假设之上，就把这层关系建模出来，以便在日后重新检查；如果复盘遵循一套有效的步骤顺序，就把这些指令做成一项技能；如果某部分工作需要重复执行某种操作，就为它构建工具；如果你总想把多个相关对象放在一起查看，就围绕这项任务构建一个视图。

我们也准备了一些尚处早期、可供继续构建的软件包：

- **au-weave：**帮助智能体从来源材料中提取知识，将其连接为类型化对象，并保留回到原始证据的链接。
- **au-competency：**帮助把领域方法转化为工作空间中的实际改动，包括类型、关系、技能、指南和工具。
- **au-govern：**帮助智能体检查类型引擎无法判断的问题，例如被引用的段落是否真的支持某项论断。
- 此外还有 **au-tree-research、au-agent-guides、au-skills、au-writing-style** 等软件包。

然后，把这套系统用到另一个真实案例中。日后的某项结果也许会挑战早期决策背后的假设，这正好可以检验：系统能否帮助你找回当时的推理，并判断哪些内容需要重新审视。先建立足以支撑工作的结构，再随着认识加深不断修改。

## 把专业知识与应用它的手段一起封装

当一种工作方式证明有效后，你就可以把可复用部分，从孕育它的那项具体工作中分离出来。

以前面的研究案例为例，可以把它做成一个 `evidence-review` 软件包，其中包含：

- 类型与方法论知识；
- 提取论断、调查共享证据的技能与工具；
- 审查论断、比较研究的交互界面。

研究者自己的论文、问题与实验结果仍留在个人项目中。有了这个软件包后，研究项目便可以声明：

```yaml
# .arsumbris/repo.yaml
name: my-research
deps:
  - name: evidence-review
```

接着，项目中的一项论断可以使用：

```yaml
type: claim::evidence-review
```

限定符指明了提供该类型的软件包。引擎会根据软件包中的 `grounds` 字段，推断嵌入其中的 `grounding` 类型。另一位研究者可以用自己的论文复用同一套系统，再针对其领域需要回答的问题进行扩展。

这也为专业人士提供了一种分发专业知识的新方式：把知识与应用知识的手段放在一起交付。法律专家可以围绕某类审查工作构建软件包，把某个事项中的事实与文件，同相关权威依据、解释和拟议变更连接起来。软件包中的方法负责指导要收集、检查什么；界面则帮助使用者审视推理，并决定接受哪些结论。另一位专家可以用自己的案件材料复用并调整整套方案。

一个软件包也可以只提供某个有用的部分：一套领域知识、一项审查技能，或一个基于其他软件包已有类型的视图。只要各软件包使用兼容的类型和关系，就能把它们组合起来。于是，对共享方法的一次改进可以惠及许多项目，而每个人仍然保有自己的工作成果和扩展。

工作留下的不该只有眼前的结果。它还可以留下一份有用的知识、一套经过又一个真实案例检验的方法，以及一个更善于承载这类工作的环境。后续项目可以在这些积累上继续前进；可复用的软件包则让其他人能够从你已经学到的东西出发，并同时获得应用这些知识所需的能力。

这就是我在知识工作工程中看到的机会：人类与智能体可以一边推进工作，一边共同发展承载这项工作的系统。

——Heinrich
